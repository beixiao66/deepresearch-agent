一、项目总体介绍

1.1 项目是什么（一句话定义）

核心定义 DeepResearch Agent 是一个基于 RAG + LangGraph 的深度研究助手：用户上传文档建立知识库（或直接上传文件），输入研究主题后，系统自动规划研究方案、经人工确认、通过多 Agent 并行检索证据，最终生成带引用溯源的中文研究报告（README.md:3）。

1.2 差异化定位（vs 同类产品）

对比维度PerplexityLangFlowDeepResearch Agent
定位面向大众的 AI 搜索问答低代码 Agent 编排平台私有知识库驱动的深度研究工具
知识来源全网搜索为主由用户搭建用户私有文档（本地知识库）
研究深度单轮回答由流程定义计划→审核→多子问题并行→聚合报告
可信度引用链接依赖构建者引用编号与证据片段一一对应，杜绝编造引用
部署形态SaaS平台本地/私有部署，数据不出域

核心差异点：Perplexity 回答"是什么"，本项目回答"基于你的文档，证据是什么"——它把研究过程变成了可审核、可溯源、可复现的工程流程，而不是单轮生成。

1.3 核心价值主张

  1. 深度研究闭环：从主题到带引用编号的完整报告，覆盖"规划 → 审核 → 并行检索 → 证据聚合 → 报告生成"全链路
  2. 可信可溯源：每个结论附 [n] 引用编号，编号与持久化证据一一对应（research.py:209-214），报告生成后还会清洗模型编造的越界引用（llm.py:159-196）
  3. 零预置门槛：支持直接上传文件发起研究（自动建临时知识库，用完即删），无需先手动建库（research.py:62-74）
  4. 成本透明：按阶段（plan / researcher / report）统计 Token 用量并展示给用户

三、核心代码解析

3.1 app/services/research_graph.py — LangGraph 多 Agent 主图

① 状态图构建方式（research_graph.py:363-392）

graph = StateGraph(ResearchState)
graph.add_node("plan", _plan_research)
graph.add_node("review", _review_plan)
graph.add_node("dispatch", _dispatch)
graph.add_node("researcher", _researcher)
graph.add_node("report", _report)
graph.add_edge(START, "plan")
...
graph.add_conditional_edges("dispatch", _fanout, ["researcher"])
graph.add_edge("researcher", "report")
graph.add_edge("report", END)
# interrupt 需要 checkpoint 保存执行现场；AsyncSqliteSaver 持久化到
# SQLite，进程重启后同一 thread_id 仍可暂停/恢复
checkpointer = await get_checkpointer()
return graph.compile(checkpointer=checkpointer)

设计思路：线性主链 + 并行子图。主链上 plan → review → dispatch → report 是强顺序（依赖关系明确），而 researcher 通过条件边并行。dispatch 节点本身是"占位"（research_graph.py:124-142），只发进度事件，真正的分发逻辑在条件边函数 _fanout 里——这是 LangGraph 的约定：Send 列表必须由条件边函数返回。

② interrupt() 人工审核机制（research_graph.py:100-121）

user_review = interrupt({
    "title": "研究计划审核",
    "question": state["question"],
    "sub_questions": state["plan"].sub_questions,
    "search_queries": state["plan"].search_queries,
})
approved = bool(user_review.get("approved"))
if not approved:
    raise ValueError("Research plan rejected by user")
  • interrupt() 的返回值是用户恢复时传入的数据（第二次 ainvoke(Command(resume={"approved": ...}))），而不是从 state 读取——实现 HITL 的语义就是"暂停问人，等人回话"
  • 函数签名是同步的（def 而非 async def），且注释明确指出 "interrupt 前没有副作用操作（可安全重放）"——这是 checkpoint 重放安全的先决条件
  • 拒绝即抛 ValueError 使任务置为 FAILED，取消路径由上层 approve_research 单独处理（research.py:179-193 置 CANCELLED）

③ Send API 多 Agent 并行分发原理（research_graph.py:145-168）

return [
    Send("researcher", {
        "question": sub_question,
        "knowledge_base_id": state["knowledge_base_id"],
        ...
    })
    for sub_question in sub_questions
]

原理：Send 是一个"消息投递"指令，每条 Send 表示"用给定的子状态启动一次 researcher 节点执行"。LangGraph 运行时并行调度这些 Send 任务，每个子 Agent 有独立的 state 快照；所有 Send 执行完毕后，用 reducer 将子状态合并回主状态（add_sub_answers），然后才进入 report 节点。注意子 Agent 之间通过 asyncio.gather 在检索层再做了一层并发（research_graph.py:219-223，每个查询词并行检索）。

④ AsyncSqliteSaver 持久化 checkpoint 如何支持暂停恢复

  • get_checkpointer()（research_graph.py）用 AsyncSqliteSaver 把执行现场持久化到 data/langgraph_checkpoints.db（config.py:checkpoint_db_path），进程重启后同一 thread_id 仍可恢复
  • 直接以 aiosqlite 连接构造（不走 from_conn_string 的 async with——那是短生命周期用法，退出上下文即关闭连接）；连接常驻进程，应用关闭时由 lifespan 调 close_checkpointer() 释放，避免 aiosqlite 后台线程阻止进程退出
  • thread_id 是关键：_build_thread_id(task_id) 用任务 ID 作为线程标识（research.py:36-45），保证跨 HTTP 请求（创建 / 批准是两个独立请求）能定位到同一执行现场
  • 序列化白名单：state 中的自定义类型 ResearchPlan 通过 JsonPlusSerializer(allowed_msgpack_modules=...) 显式注册（jsonplus 序列化器对未注册类型会告警，未来版本将直接拒绝）

3.2 app/services/document_retriever.py — 混合检索管线

① 双路召回（document_retriever.py:64-78）

  • 稠密路：查询 embedding → Qdrant 按 knowledge_base_id payload 过滤的 query_points（qdrant_store.py:150-185），取 max(limit, sparse_limit) 即 10 条
  • 稀疏路：SparseRetriever.search()（sparse_retriever.py:49-89）对 FTS5 虚拟表执行 MATCH 查询，-bm25() 取反使分数"越高越相关"
  • FTS5 查询安全：build_match_query()（sparse_retriever.py:18-34）把用户查询拆 token、转义 FTS5 特殊字符（"*:^~()-）、加引号、AND 连接——用户输入 step-by-step 会直接破坏 MATCH 语法，这是容易踩坑的细节

② RRF 融合的排序原理（rrf.py:20-56）

for rank, (document_id, chunk_index, text) in enumerate(ranked_list, start=1):
    key = (document_id, chunk_index)
    scores[key] = scores.get(key, 0.0) + 1.0 / (K_CONSTANT + rank)

核心思想（rrf.py:1-5 注释写得很清楚）：两路分数量纲不同不可比，只比较排名。每路第 rank 名的贡献是 1/(60+rank)（k=60 经验常数），同名片段跨路累加，最终按融合分降序取 top-N。这让 BM25 的负数分数与余弦相似度无需归一化即可融合。

③ Rerank 精排的调用方式（document_retriever.py:122-142）

_rerank_fused 把融合结果交给 reranker.rerank(query, documents, top_n) 做交叉编码器打分（qwen3-rerank），然后用 relevance_score 重建 FusionItem。注意这里丢弃了 RRF 分数、完全由精排分数决定最终排序——Rerank 是"最后一公里"的排序权威。

3.3 app/services/llm.py — LLM 调用统一封装

① Token 用量统计（llm.py:29-38）

def _record_usage(counters: dict, response) -> None:
    metadata = getattr(response, "usage_metadata", None) or {}
    counters["prompt_tokens"] += metadata.get("input_tokens", 0)
    counters["completion_tokens"] += metadata.get("output_tokens", 0)
    counters["total_tokens"] += metadata.get("total_tokens", 0)

设计模式：每个节点传入自己的计数器 dict，函数内累加。配合 state.py:17-44 的 merge_token_usage reducer，并行子 Agent 的用量在状态合并时自动按阶段（plan/researcher/report）累加，最终持久化到 research_tasks.token_usage（research.py:263-268）并在报告页展示。

② 研究计划的结构化输出（llm.py:60-75）

result = await get_llm().with_structured_output(
    ResearchPlan, include_raw=True,
).ainvoke(messages)
if isinstance(result, dict):
    raw_message = result.get("raw")
    if usage_counters is not None and raw_message is not None:
        _record_usage(usage_counters, raw_message)
    return result.get("parsed")

include_raw=True 是为拿 token 用量而设计：默认 with_structured_output 只返回解析结果，拿不到原始响应的 usage_metadata，所以返回 {"raw": AIMessage, "parsed": ResearchPlan}，从 raw 里提取用量。同时做了版本兜底（某些版本直接返回 plan）。

③ 引用编号清洗的正则处理逻辑（llm.py:143-196）

这是"防编造引用"的工程化处理，分四种情况：

正则处理示例
\[(\d+)\]\s*[–—-]\s*\[(\d+)\]区间超范围 → 截断到 [N][1]–[5] 且 max=3 → [1]-[3]
\[(\d+)\]\s*[–—-]\s*(?!\[)残缺区间 → 整体删除[1]– 后无编号 → 删除
\[(\d+)\]单个超范围编号 → 删编号留正文[9] 且 max=5 → 删除
[（(]\s*基于\s*[）)]残留空壳括号 → 删除（基于 ） → 删除

配合 system prompt 中的"资料编号范围是 [1] 到 [N]""不要编造编号"双保险（llm.py:216-219），以及末尾推荐段截断（_strip_promotional_tail，llm.py:128-140，11 个模式如"如需帮助"），报告质量的后处理相当完备。

3.4 app/services/sse.py — SSE 流式响应

① 流式实现

两个 generator 函数（stream_start_research / stream_approve_research）被路由层包进 StreamingResponse(media_type="text/event-stream")，并设 Cache-Control: no-cache + X-Accel-Buffering: no（research.py:88-99，后者是 Nginx 反代时禁缓冲的关键）。事件格式 data: {json}\n\n（sse.py:19-21）。

② 进度事件钩子（hook）的设计模式（sse.py:24-31 + research_graph.py:39-50）

_progress_hook = None          # 模块级全局钩子
def set_progress_hook(hook):
    global _progress_hook
    _progress_hook = hook
def _emit(event):
    if _progress_hook is not None:
        _progress_hook(event)

这是观察者模式的轻量实现：图节点只调 _emit() 发事件，不感知 SSE 存在；服务层注入队列回调，测试 / 普通调用不注入即为 no-op。解耦了图执行与传输层，是测试友好（143 个测试可 mock）的关键设计。

③ 临时知识库的创建与清理机制（sse.py:41-93）

上传附件研究时建了临时知识库（前缀"研究附件-"，research.py:28、62-74），任务结束后在 finally 中删除。但直接删会踩坑：

# research_tasks.knowledge_base_id 外键是 ON DELETE CASCADE，
# 直接删知识库会把研究任务记录也级联删掉
await knowledge_base_service.session.execute(text("PRAGMA foreign_keys=OFF"))
try:
    await knowledge_base_service.delete(task.knowledge_base_id)
finally:
    await knowledge_base_service.session.execute(text("PRAGMA foreign_keys=ON"))

注释（sse.py:49-55）把原因讲透了：先验前缀确认是临时库，再临时关外键避免级联删掉任务记录，finally 恢复——这是对 SQLite 外键语义的精确驾驭。

五、项目不足与改进建议

5.1 已知局限（README 自述 + 评估数据解读）

① SQLite FTS5 中文分词效果差

评估数据（README.md:137-141）显示纯向量与混合检索指标完全相同（DocR@5 / ChunkR@5 均 0.960），说明 BM25 路对中文查询零增益。根因：FTS5 默认 unicode61 tokenizer 按空格 / 标点切词，中文无空格，连续中文串被当作超长单 token，MATCH 几乎命中不到查询词。改进方向（README 已提到）：jieba 分词预处理 + FTS5 自定义 tokenizer（或换用 SQLite ICU tokenizer），需重建索引。

② 纯向量与混合检索指标一致的原因分析

RRF 融合后两路结果与纯向量一致，意味着融合结果被稠密路主导。在 BM25 无效的情况下，RRF 只是给稠密结果重新排了一次序（排名相同则融合分排序与单路一致）。Rerank 才是真正拉开差距的环节：ChunkMRR 0.814 → 0.968（+0.154），说明混合检索的价值排序是"向量召回保障覆盖，Rerank 保障精度"——当前 Rerank 是最大的单点提升。

附：Perplexity 和 LangFlow 是什么？

这两个词是报告里用来做对比参照的产品。它们是国外比较知名的 AI 产品，下面用"零前置知识"的方式解释。

Perplexity —— "AI 版搜索引擎"

是什么：一个 AI 问答搜索引擎（perplexity.ai）。用法跟 Google 一样：输入问题 → 它实时搜索全网网页 → 用大模型把内容综合成一段带引用来源的直接回答，而不是给你一列链接。

和 ChatGPT / Google 的区别：ChatGPT 靠模型"记忆"回答（可能过时、可能编造）；Google 给你一堆链接自己读；Perplexity 是当场搜索、当场总结、当场附引用，答案更新且可溯源。

为什么报告里提到它：它代表"全网公开知识问答"这类产品。本项目的差异点是——资料源是用户私有文档、流程是"规划 → 人工审核 → 多 Agent 并行深挖 → 聚合报告"。它做广度的单轮问答，本项目做私有知识库上的深度研究。

LangFlow —— "可视化 AI 应用搭建平台"

是什么：一个开源的低代码工具，用来拖拽式搭建 LLM 应用（聊天机器人、RAG、Agent 工作流）。左边栏是"模型调用、向量检索、工具"等积木块，拖到画布上用线连起来就是一条工作流，一键运行部署。可以理解为 AI 版的 ComfyUI，底层基于 LangChain/LangGraph 生态。

为什么报告里提到它：它代表"通用平台"——流程怎么走由搭建者自己设计，需要拖节点、写配置；本项目则是"垂直成品"——把深度研究这个领域的最佳实践固化成了开箱即用的产品，用户只需上传文档、输入主题，不用任何搭建能力。

一句话总结 Perplexity 是"AI 搜索引擎"，LangFlow 是"搭 AI 应用的可视化工具"。提到它们是为了说明本项目的定位——做它们都没做的"私有知识库 + 可审核多 Agent 深度研究"细分场景。

零前置知识的介绍话术（面试备选）

如果你在面试或给同学介绍时怕对方也不知道这两个名字，可以直接换成更通俗的说法：

"和普通的 AI 问答（比如 ChatGPT 这种）不一样，我的项目是基于你自己的文档做深度研究——用户上传资料，系统规划方案、人工确认、多个 AI 研究员并行检索证据，最后给出带引用的报告。"

这样完全不需要先解释两个陌生产品。
